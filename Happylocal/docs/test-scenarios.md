# 테스트 시나리오

두 종류입니다.

- **업무흐름 시나리오** — 한 역할이 하루 동안 하는 일을 순서대로 따라갑니다.
- **연계 시나리오** — 여러 역할이 하나의 대상을 두고 맞물리는 지점을 봅니다.

시나리오 번호는 실행본 `server/src/scenariotest.js` 의 이름과 1:1 로 맞춰
두었습니다. 문서를 고치면 실행본도 같이 고칩니다.

```bash
npm run seed:accounts     # 역할별 계정 준비 (한 번)
npm run test:scenario     # 아래 시나리오를 실제로 실행
```

**판정 원칙**: "오류가 안 났다" 가 아니라 **"숫자와 상태가 맞다"** 로 봅니다.
화면이 멀쩡한데 값이 틀린 결함을 여러 번 겪었기 때문입니다.

## 1. 업무흐름 시나리오

### W1. 일반 사용자 — 처음 와서 픽업까지

계정 `customer1` · 앱 `/happylocal_v2.html`

| # | 하는 일 | 확인할 것 |
|---|---|---|
| 1 | 로그인하지 않고 둘러본다 | 홈·지도·코스·캘린더가 전부 보인다 |
| 2 | 예약을 누른다 | 로그인 안내가 뜨고 예약은 막힌다 |
| 3 | 회원가입한다 | 가입 즉시 로그인되고 **쿠폰 3장**이 들어온다 |
| 4 | 지역을 평창으로 바꾼다 | 목록에 평창 상품만 남는다 |
| 5 | 상품을 열어 수량을 올린다 | **재고보다 많이 담기지 않는다** |
| 6 | 결제 화면에서 쿠폰을 고른다 | 총액 = 정가×수량 − 할인 − 쿠폰 |
| 7 | 결제한다 | 재고가 주문 수량만큼 줄고, 예약코드가 나온다 |
| 8 | 장바구니에서 픽업 코드를 연다 | 화면 코드 = 실제 예약코드 |
| 9 | 새로고침한다 | 예약이 그대로 있다 (서버가 정본) |
| 10 | 예약을 취소한다 | 재고와 쿠폰이 **둘 다** 되돌아온다 |

> 6·10 이 핵심입니다. 예전에는 쿠폰이 3,000원 고정이었고, 취소해도 쿠폰이
> 돌아오지 않았습니다.

### W2. 생산자 — 아침 출하부터 정산까지

계정 `farmer_hs` · 운영 화면 `/admin.html`

| # | 하는 일 | 확인할 것 |
|---|---|---|
| 1 | 로그인한다 | **오늘 출하 · 판매 현황 · 정산** 세 메뉴만 보인다 |
| 2 | 오늘 출하를 연다 | 담당(횡성) 상품만 보이고 재고가 낮은 것이 눈에 띈다 |
| 3 | 한우 등심에 5개를 넣는다 | 재고가 정확히 +5, 이력에 `restock +5` 가 남는다 |
| 4 | 앱에서 그 상품을 본다 | 앱 재고도 같이 늘어 있다 |
| 5 | 가격을 바꿔 본다 | 판매가 > 정가는 거부된다 |
| 6 | 남의 지역 상품을 만져 본다 | 404 (존재 여부도 알려주지 않는다) |
| 7 | 판매 현황을 연다 | 수령완료 건만 매출로 잡힌다 |
| 8 | 정산을 연다 | 지급액 = 판매액 − 수수료, 이번 달이 기본 |

> 3 이 없으면 재고는 줄기만 하고 며칠이면 전 상품이 품절됩니다.
> 이 흐름이 이 서비스가 매일 돌아가는 이유입니다.

### W3. 매장 관리인 — 카운터에서 마감까지

계정 `store_hanwoo` · 운영 화면

| # | 하는 일 | 확인할 것 |
|---|---|---|
| 1 | 로그인한다 | **오늘 픽업 · 일일 마감 · 매장 정보** 세 메뉴 |
| 2 | 오늘 픽업을 연다 | 담당 거점 예약만, 대기 건이 위로 |
| 3 | 손님이 댄 코드를 입력한다 | 소문자로 넣어도 찾는다 |
| 4 | 수령 확인을 누른다 | 상태 `completed`, **재고는 그대로** |
| 5 | 같은 코드를 다시 조회한다 | "이미 처리된 예약" 안내, 버튼 없음 |
| 6 | 다른 매장 코드를 넣어 본다 | 404 |
| 7 | 안 온 예약을 노쇼 처리한다 | 재고 복구 여부를 **고를 수 있다** |
| 8 | 파손 상품 재고를 뺀다 | **사유 없이는 거부**, 재고보다 많이 빼도 거부 |
| 9 | 일일 마감을 연다 | 대기/수령/취소/노쇼 + 매출 |

> 4 의 "재고는 그대로" 가 중요합니다. 재고는 예약 시점에 이미 빠졌으므로
> 수령 확인에서 또 빼면 이중 차감입니다.

### W4. 운영자 — 콘텐츠와 캠페인

계정 `operator1` · 운영 화면

| # | 하는 일 | 확인할 것 |
|---|---|---|
| 1 | 로그인한다 | 콘텐츠·쿠폰·후기·통계 (매장/농가 메뉴 없음) |
| 2 | 공지를 고친다 | 앱 공지 화면에 바로 반영된다 |
| 3 | 공지를 통째로 비워 본다 | `409 WOULD_EMPTY` 로 막힌다 |
| 4 | 허용되지 않은 키를 열어 본다 | 404 (화이트리스트 밖) |
| 5 | 쿠폰을 발행한다 | 전체 회원에게 들어가고 감사 로그에 남는다 |
| 6 | 부적절한 후기를 숨긴다 | 앱 목록에서 사라진다 |
| 7 | 계정 관리를 열어 본다 | 403 (운영자 권한 밖) |

> 3 이 없으면 실수로 저장 한 번에 앱 공지가 빈 채로 배포됩니다.

### W5. 최고관리자 — 입점 심사와 정산 집행

계정 `admin1` · 운영 화면

| # | 하는 일 | 확인할 것 |
|---|---|---|
| 1 | 로그인한다 | 14개 메뉴 전부 |
| 2 | 입점 심사를 연다 | 심사 대기 신청이 보인다 |
| 3 | 승인한다 | **그 자리에서 역할과 범위가 붙는다** |
| 4 | 계정·역할에서 직접 부여해 본다 | 부여 즉시 그 계정이 쓸 수 있다 |
| 5 | 회수한다 | 즉시 차단된다 |
| 6 | 마지막 관리자 권한을 뺀다 | `409 LAST_ADMIN` 으로 막힌다 |
| 7 | 계정을 정지한다 | 그 계정은 로그인 자체가 안 된다 |
| 8 | 정산 집행을 연다 | 농가별 지급액, 수식이 맞다 |
| 9 | 지급 처리한다 | 두 번째는 `409 ALREADY_PAID` |
| 10 | 감사 로그를 연다 | 위 행위들이 남아 있다 |

> 6 이 없으면 관리자가 실수로 자기 권한을 내려놓고 아무도 되돌릴 수 없게
> 됩니다.

### W6. 입점 신청자 — 밖에서 안으로

계정: 새로 가입한 일반 사용자

| # | 하는 일 | 확인할 것 |
|---|---|---|

## 2. 연계 시나리오

역할 하나만 보면 멀쩡한데 이어 붙이면 어긋나는 지점들입니다.

### L1. 한 건의 픽업이 세 역할을 지나간다

```
[생산자]   출하 5개        stock 4 → 9      restock 로그
[일반]     2개 예약        stock 9 → 7      status=reserved, code 발급
[매장]     코드 조회       내 거점 것만 나온다
[매장]     수령 확인       status=completed, stock 7 (변화 없음)
[일반]     앱 새로고침      "픽업완료" 로 보인다
[생산자]   판매 현황       완료 1건, 매출 반영
[관리자]   정산            지급액 = 판매액 − 수수료
```

**확인**: 재고 수지가 `9 − 2 = 7` 로 끝까지 맞고, `completed` 가 정산까지
흘러간다. 수령 확인이 재고를 다시 빼지 않는다.

### L2. 재고 하나를 두고 세 사람이 움직인다

```
[생산자]  출하 +5
[손님A]   3개 예약        stock -3
[손님B]   3개 예약        재고 부족이면 409, 성공하면 stock -3
[매장]    파손 1개 차감    사유 필수
[매장]    손님A 노쇼(복구)  stock +3
```

**확인**: 어떤 순서로 와도 재고가 **음수로 내려가지 않는다.**
동시에 재고보다 많은 요청을 던져도 성공 건수 = 초기 재고.

### L3. 쿠폰이 주문·취소를 오간다

```
[손님]   쿠폰 선택 후 결제   couponDiscount 적용, 쿠폰 used=true
[손님]   같은 쿠폰 재사용     409
[손님]   주문 취소           쿠폰 used=false, 재고 복구
[손님]   다시 그 쿠폰 사용    성공
[매장]   노쇼 처리           쿠폰은 돌려주지 않는다 (손님 사정)
```

**확인**: 취소와 노쇼의 쿠폰 처리가 **다르다**. 취소는 돌려주고 노쇼는 아니다.

### L4. 역할 부여가 즉시 반영된다

```
[관리자] customer2 에게 operator 부여
[customer2] 다시 로그인 → 콘텐츠 편집 가능
[관리자] 회수
[customer2] 즉시 403
[관리자] 계정 정지
[customer2] 로그인 자체가 403 SUSPENDED
```

### L5. 두 매장이 서로를 보지 못한다

```
[손님]     A 거점 상품 예약
[A 매장]   목록에 보인다, 수령 확인 가능
[B 매장]   목록에 없다, 코드 조회 404, 수령 확인 404
[손님]     B 거점 상품도 예약
[B 매장]   자기 것만 보인다
```

**확인**: 목록·조회·조작 **세 경로 모두** 막혀야 한다. 하나라도 뚫리면
격리가 아니다.

### L6. 콘텐츠 변경이 앱까지 간다

```
[운영자] 공지 수정
[앱]     공지 화면에 반영
[운영자] 후기 숨김
[앱]     후기 목록에서 사라짐
[운영자] 쿠폰 발행
[손님]   쿠폰함에 들어와 있음
```

### L7. 정산은 실제로 찾아간 것만 센다

```
[손님]  3건 예약
[매장]  1건 수령 확인 / 1건 노쇼 / 1건은 그대로 대기
[정산]  1건만 잡힌다
```

**확인**: `reserved` 와 `noshow` 는 돈이 오가지 않으므로 정산에서 빠진다.

### L8. 재고 표시가 모든 화면에서 같다

```
[생산자] 출하 +7
확인:  운영 화면 재고 = 서버 재고
      앱 상품 목록 재고 = 서버 재고
      앱 매장 목록 "N개 남음" = 서버 재고
      수량 상한 = 서버 재고
```

> 예전에는 매장 목록의 "오늘 12팩 남음" 이 시드에 박힌 문자열이라 실제
> 재고가 4개여도 그대로였고, 그 숫자가 수량 상한까지 정했습니다.

## 3. 실행본과의 대응

| 시나리오 | 실행 위치 |
|---|---|
| W1 | `logintest.js` · `uilogictest.js` · `e2etest.js` |
| W2 · W3 | `scenariotest.js` · `admintest.js` |
| W4 · W5 · W6 | `scenariotest.js` · `roletest.js` |
| L1 | `scenariotest.js` (연계 흐름) |
| L2 · L3 | `logictest.js` (재고 수지 · 쿠폰) |
| L4 · L5 | `accounttest.js` · `roletest.js` |
| L6 · L7 · L8 | `scenariotest.js` |

수동으로만 확인할 수 있는 것은 **카카오 OAuth 왕복** 하나입니다.
외부 인증 서버를 오가므로 자동화하지 않았습니다.
